# Диагностика DTC в DiLink 2

Перенесено из AndyShaman/BYDMate, коммит
`ddb6046e076dc50461cb71bab78b5fafa5cc1039` (проверен 06.11.2026).
Основная лицензия проекта распространяется и на перенесённые исходники.

Вход: **Настройки → Сервис и данные → Диагностика ошибок**.
Чтение запускается только вручную. Последний завершённый результат сохраняется
между перезапусками; дата и число ответивших блоков показаны явно. Активные,
сохранённые и ожидающие подтверждения коды различаются. Описания из таблиц
оригинала — на английском; совпадения только с похожими моделями помечаются.
Telegram использует существующие настройки бота в «Интеграциях» и отправляется
по отдельной кнопке, без автоматической рассылки и без повторов из очереди.

Стирание требует подтверждения, свежего сканирования (10 минут), свежей
телеметрии, положения P и достоверно нулевой скорости. Эти ограничения не
связаны с ослабленными ограничениями дистанционного управления климатом.
Шлюз повторно проверяет P, скорость, диагностическую службу и занятость перед
каждой командой; адреса и UDS-команды ограничены списком из оригинала.
После стирания выполняется повторное чтение. Потеря подтверждения не означает
успех: неизвестные результаты блокируют повторное стирание до нового скана.
Начало диагностической операции не переотправляется после обрыва Binder.

## Совместимость

Протокол оригинала работает через BYDAutoMqttDevice (1033), штатную службу
диагностики и `sys.diagmgrsrv.task_bk`. На проверенной старой CANFD-прошивке
менеджера нет, но найден и физически проверен другой контейнер того же MQTT
канала (описан ниже). Неизвестные прошивки не получают этот обход проверки.
Адреса gear/speed взяты из существующего FidMap нашего форка.
На проверенном старом CANFD стирание полностью запрещено.

Классы BYD вынесены в compileOnly-модуль `bydauto-stubs`: они не должны попадать
в APK, так как реальная реализация предоставляется прошивкой. После обновления
APK нужен новый процесс helper, старый не знает новых Binder-команд (62–64).

## Резервный канал helper

На Чайке подтверждён отказ SELinux `add` для `bydmate_helper`: shell-процесс не
может зарегистрировать произвольный сервис через ServiceManager. Перенесён
резервный механизм оригинала из того же коммита: явный broadcast с Binder,
проверка случайного токена конкретного запуска и дескриптора, отслеживание смерти
процесса и повторная доставка после перезапуска приложения. UID-проверка команд
helper сохранена. SELinux не отключается, root не требуется.

Bootstrap проверяет версию живого helper, а не только сохранённую версию;
команды запуска/подтверждения клиента используют слоты оригинала (29 и 44).
Первый broadcast может запустить обновлённое приложение, последующие не отменяют
явную остановку пользователем. После подтверждения клиента рассылка прекращается.

## Проверка на машине

### DiLink 2 CANFD: чтение сохранённого кэша

На `mt6765 / k65v1_64_bsp / CANFD / mtk_2.1h.202312130_canfd`
наличие `diagnosticsrv` не означает наличие нового менеджера UDS. Исследованный
`diagnosticsrv` содержит в том числе самодиагностику USB, антенн и touchscreen.
В SDK присутствуют MQTT device 1033, DTC device 1045 и OTA device 1032.
`BYDAutoDtcDevice.sendFaultCodeData` — отправка данных, не доказанный метод
чтения ошибок ЭБУ; он не вызывается.

Байт-код `BYDAutoOtaDevice.getFaultCodeInfo()` обращается к 1032/FID 815 через
`getBuffer`. Дизассемблирование `libbydauto.so` подтвердило Binder-транзакцию
**13**; транзакция 9 на этой прошивке является `getIntArray`, её служебные
значения нельзя разбирать как диагностический буфер. Ручная проверка в P
вернула для GET 13/1032/815 статус 0, длину 0: кэш пуст, отсутствие неисправностей
**не подтверждено**. Скорость в этот момент была недоступна (-1).

Для точного проверенного профиля добавлен отдельный режим чтения кэша через
helper (слот 65), с ограничением размера и фильтрацией ошибок/сентинелов.
Пустые и неизвестные данные не превращаются в «ошибок нет». Telegram получает
отчёт о чтении кэша, а не выдуманный результат сканирования. Кнопок стирания нет,
репозиторий и helper также запрещают стирание для этого профиля. Кэш оставлен
дополнительным инструментом; его формат при непустом ответе пока не декодируется.
Основной сканер теперь выполняет активные запросы чтения (см. ниже), без OTA,
сеансов программирования и стирания. Установка нового интерфейса на ГУ пока
не выполнялась. После восстановления
Remote ADB прочитаны реальные константы SDK (через небольшую утилиту отражения,
без вызова автомобильных команд):

- MQTT device 1033: `MQTT_DIAGNOSE_RESULT=0x9900010A`,
  `MQTT_DIAGNOSE_RESULT_SET=0xAA00010A`, `MQTT_DIAGNOSE_GUID_UUID=0x9900010B`;
  все три присутствуют в штатной карте возможностей MQTT.
- OTA: `OTA_CMD_ECU_GET_FAULTCODE=815`, `OTA_CMD_ECU_GET_FAULTCODE_SET=816`.
- DTC: `DTC_SET_FAULT_CODE_SET=0xAA000046`; CANFD remote-diag control
  `DTC_REMOTE_DIAG_SET=0x49A0002F` (не путать с CAN-значением `0x49A0042F`).

Наличие SET-констант само по себе не подтверждает формат запроса. FID 816,
`DTC_SET_FAULT_CODE_SET` и `DTC_REMOTE_DIAG_SET` не вызывались. Полный локальный
прогон после добавления режима кэша: 3005 тестов, 0 ошибок, 2 пропущены.
Публичный 3.9.1 не изменялся.

### DiLink 2 CANFD: активное чтение ЭБУ (3.9.2)

Байт-код штатного OTAUpdate, метод
`CheckVersionDownloadPresenter$OtaDiagnoseEcuInfoListener.sendRequestEcuSoftVersionCode`,
подтвердил старый контейнер `01 addr(2) len uds…` вместо `0A`. Ответ имеет тот же
7-байтный заголовок, но тоже начинается с `01`. Первый одиночный запрос
`01 07 E0 03 19 01 FF` получил `01 07 E8 06 01 01 01 59 01 09 00 00 00`
с нулевым заполнением до 512 байт: настоящий ответ ЭБУ 0x7E0 с нулевым счётчиком.

`CanFdReadOnlyDevice` переводит только точный список разрешённых запросов:
`19 01 FF`, `19 02 0D/09/FF`, `19 04 <DTC> FF`, `22 F1 94`, `22 F1 97`.
Адреса ограничены существующим списком из 18. Другие сервисы, включая стирание,
сброс, смену сеанса и security access, отвергаются до транспорта.
Неизвестный префикс ответа не принимается как ответ нашего запроса.

Допуск действует только для точного профиля из предыдущего раздела. Перед
каждым запросом нужны свежая P, отсутствие нового диагностического менеджера,
`getInt(1032, 0x43400030) == 0` и `persist.sys.byd.otaupdate == false`.
Неизвестное состояние OTA запрещает чтение. Нужна подтверждённая регистрация
RX, пассивная тишина перед началом; чужой кадр прекращает проход, кроме точных
дубликатов наших ответов. Действуют прежние паузы и бюджет 90 секунд.
Это снижает риск конфликта, но не является атомарной блокировкой штатного OTA;
совместный запуск диагностики и обновления прошивки не поддерживается.
