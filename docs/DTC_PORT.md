# Диагностика DTC в DiLink 2

Перенесено из AndyShaman/BYDMate, коммит
`ddb6046e076dc50461cb71bab78b5fafa5cc1039` (проверен 06.11.2026).
Основная лицензия проекта распространяется и на перенесённые исходники.

Вход: **Настройки → Сервис и данные → Диагностика ошибок**.
Чтение запускается только вручную. Последний завершённый результат сохраняется
между перезапусками; дата и число ответивших блоков показаны явно. Активные,
сохранённые и ожидающие подтверждения коды различаются. Описания из таблиц
оригинала — на английском; совпадения только с похожими моделями помечаются.
Telegram использует существующие настройки бота в «Интеграциях» и отправляется
по отдельной кнопке, без автоматической рассылки и без повторов из очереди.

Стирание требует подтверждения, свежего сканирования (10 минут), свежей
телеметрии, положения P и достоверно нулевой скорости. Эти ограничения не
связаны с ослабленными ограничениями дистанционного управления климатом.
Шлюз повторно проверяет P, скорость, диагностическую службу и занятость перед
каждой командой; адреса и UDS-команды ограничены списком из оригинала.
После стирания выполняется повторное чтение. Потеря подтверждения не означает
успех: неизвестные результаты блокируют повторное стирание до нового скана.
Начало диагностической операции не переотправляется после обрыва Binder.

## Совместимость

Протокол оригинала работает через BYDAutoMqttDevice (1033), штатную службу
диагностики и `sys.diagmgrsrv.task_bk`. Наличие этих механизмов на конкретной
прошивке Seagull/DiLink 2 **ещё не проверено физически**. При их отсутствии
показывается недоступность, а не «ошибок нет». Адреса gear/speed взяты из
существующего FidMap нашего форка. Неизвестная скорость запрещает стирание.

Классы BYD вынесены в compileOnly-модуль `bydauto-stubs`: они не должны попадать
в APK, так как реальная реализация предоставляется прошивкой. После обновления
APK нужен новый процесс helper, старый не знает новых Binder-команд (62–64).

## Резервный канал helper

На Чайке подтверждён отказ SELinux `add` для `bydmate_helper`: shell-процесс не
может зарегистрировать произвольный сервис через ServiceManager. Перенесён
резервный механизм оригинала из того же коммита: явный broadcast с Binder,
проверка случайного токена конкретного запуска и дескриптора, отслеживание смерти
процесса и повторная доставка после перезапуска приложения. UID-проверка команд
helper сохранена. SELinux не отключается, root не требуется.

Bootstrap проверяет версию живого helper, а не только сохранённую версию;
команды запуска/подтверждения клиента используют слоты оригинала (29 и 44).
Первый broadcast может запустить обновлённое приложение, последующие не отменяют
явную остановку пользователем. После подтверждения клиента рассылка прекращается.

## Проверка на машине

1. Обнаружить ADB-устройство по adb-discovery, подтвердить физическую цель.
2. Установить APK, перезапустить helper, убедиться в свежих данных и P.
3. Сначала **только чтение**: проверить диагностическую службу, ответы блоков,
   список кодов, корректность расшифровок и отправку отчёта в Telegram.
4. Перед стиранием сохранить отчёт; стирание проверять отдельно с владельцем,
   без других диагностических программ, на неподвижной машине.
5. Сверить повторный скан: активные неисправности могут появиться снова.

Локальные тесты: `:app:testPhysicalDebugUnitTest --tests
'com.bydmate.app.data.dtc.*' --tests 'com.bydmate.app.helper.dtc.*'`.
